Add a minimal MULTI-SCREEN UI SHELL and dedicated UI PLAYGROUND.

This milestone is about navigation structure only.

Do NOT implement the new optimistic UI state architecture yet.
Do NOT implement Sonos event subscriptions yet.
Do NOT implement grouping yet.
Do NOT redesign the existing useful Now Playing UI.
Do NOT build a general widget framework.
Do NOT add historical checkpoint documentation.

Read the current UI, hardware button semantics, touch handling, AppState, power behavior,
and docs before changing anything.

==================================================
1. PRODUCT GOAL
==================================================

The controller needs room for richer interactions without making every touch target
tiny or relying on invisible global swipe gestures.

Introduce three conceptual screens:

  NOW PLAYING
  GROUPING
  PLAYGROUND

Initially:

NOW PLAYING
  existing useful playback UI

GROUPING
  placeholder / shell only in this milestone

PLAYGROUND
  dedicated area for interaction experiments

Do not implement grouping functionality yet.

==================================================
2. HARDWARE-BUTTON SCREEN NAVIGATION
==================================================

Use an appropriate existing physical hardware button to cycle screens.

Desired behavior:

  Now Playing
      ->
  Grouping
      ->
  Playground
      ->
  Now Playing

Use ONE explicit short-press action.

Do not use:

- global swipe navigation
- edge gestures
- hidden touch zones
- double/triple click navigation
- long-press navigation

Touch should remain local to the currently visible screen.

Choose the physical button based on current hardware semantics and avoid conflicting
with important existing controls.

If no currently unused/simple physical button exists, inspect current behavior and make
the smallest sensible reassignment rather than layering ambiguous gestures.

==================================================
3. SCREEN NAVIGATION STATE
==================================================

Model active screen separately from Sonos/application state.

Conceptually:

  ScreenNavigationState
    activeScreen

This is UI navigation state.

It is NOT:

- ObservedState
- PendingState
- Sonos state
- device config
- room state

Changing screens must never itself mutate Sonos.

Do not persist active screen across reboot/sleep.

Fresh boot may start at Now Playing.

==================================================
4. SCREEN-LOCAL INTERACTION
==================================================

Each screen may have ephemeral local interaction state.

When leaving a screen:

- cancel/release active touch interactions owned by that screen
- do not cancel already accepted Sonos mutations
- do not alter observed Sonos state
- do not alter grouping
- do not alter selected room

A touch started on one screen must never complete against controls on another screen.

==================================================
5. MINIMAL SCREEN INTERFACE
==================================================

Introduce only the smallest abstraction justified by multiple screens.

Conceptually something like:

  Screen
    onEnter()
    onLeave()
    handleTouch(...)
    render(...)

and:

  ScreenManager
    active screen
    next()

Exact names/design are implementation choices.

Do not create:

- generic widget hierarchy
- virtual DOM
- animation framework
- layout engine
- navigation stack
- router

We need three screens and explicit lifecycle/ownership, not a UI framework.

==================================================
6. NOW PLAYING
==================================================

Preserve the current accepted Now Playing behavior as much as possible.

Move/adapt it behind the screen abstraction without opportunistic redesign.

Existing:

- artwork
- metadata
- play/pause
- volume
- room behavior
- queue interaction
- current touch calibration

should remain functional.

This milestone should not change how Sonos synchronization works.

==================================================
7. GROUPING PLACEHOLDER
==================================================

Add a Grouping screen shell.

It may simply display:

  GROUPING
  Coming next

or equivalent development UI.

Do not implement group mutations or topology UI yet.

The purpose is to establish navigation space for the later grouping milestone.

==================================================
8. PLAYGROUND
==================================================

Add a clearly development-oriented Playground screen.

The Playground exists to exercise future interaction/state models against real
application data without requiring those experiments to become permanent product UI.

Initially give it only enough UI to prove:

- screen-specific touch handling
- rendering
- local ephemeral state
- large touch targets

For example:

- a large draggable local-only control
- a large toggle/button
- visible touch coordinates/state

These controls do NOT need to mutate Sonos in this milestone.

Keep the layout disposable.

Do not make Playground a fake production screen.

==================================================
9. TOUCH OWNERSHIP
==================================================

Touch dispatch must go only to the active screen.

No screen should independently poll global touch state and accidentally react while
hidden.

A screen transition must clear/cancel active touch ownership.

Preserve current touch calibration in the hardware adapter.

==================================================
10. POWER / ACTIVITY
==================================================

Physical screen-navigation presses count as local activity.

Touch interactions on any screen count according to existing local activity semantics.

Changing screens does not otherwise alter sleep behavior.

On wake/reboot:

  active screen = Now Playing

unless a current durable product rule strongly suggests otherwise.

==================================================
11. DOCS/HARDWARE
==================================================

If physical button semantics change, update the existing hardware button/state diagram.

Document only current behavior.

Do not add milestone history.

==================================================
12. TESTS
==================================================

Add portable tests where practical for:

- default screen = Now Playing
- next cycles through all three screens
- cycle wraps
- changing screen does not mutate Sonos
- touch goes only to active screen
- leaving screen cancels local active interaction
- accepted Sonos work survives screen change
- wake/fresh boot starts on Now Playing
- screen navigation records local activity

Keep existing UI tests passing.

==================================================
13. GREEN BASELINE
==================================================

Run current canonical formatting/check/build tasks.

Keep both current hardware targets green.

==================================================
14. COMPLETION
==================================================

Stop when:

1. Now Playing, Grouping, and Playground screens exist
2. one explicit physical-button action cycles them
3. no global swipe navigation exists
4. Now Playing retains existing behavior
5. Grouping is only a placeholder
6. Playground can host disposable touch experiments
7. touch ownership is screen-local
8. screen changes do not mutate Sonos
9. docs reflect any changed button semantics
10. all checks/builds pass

Then report only:

- chosen screen-navigation button
- final screen lifecycle abstraction
- what exists on Playground
- any regression or limitation discovered

Do not begin the state-model milestone automatically.
