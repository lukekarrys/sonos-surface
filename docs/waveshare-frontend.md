# Waveshare 1.8-inch frontend

## Deliberate UI contract

The Waveshare build has three top-level screens cycled by the BOOT button (Now Playing, Grouping, Playground; see [screens](#screens-and-lvgl-architecture)). Now Playing is the product UI: a now-playing view, a room selector, and a four-item queue browser as its sub-views. It consumes normalized AppState/QueuePage and emits explicit MusicIntent values or device navigation actions. The interaction and rendering code never interprets Sonos SOAP, classifies service URIs, or calls the network. A separate device artwork worker performs bounded image GETs and decoding. Stick keeps its own UI. The [room/policy model](policy.md) and [shared capability contract](sonos-capabilities.md) remain authoritative.

| Control | Interaction |
| --- | --- |
| Room header | Open the currently configured, resolved, eligible rooms; tap one to select, or Back to dismiss |
| Previous / Play or Pause / Next | One explicit transport intent on release; Play/Pause label follows the observed state |
| Volume | Preview an absolute 0–100 value while touching, submit once on release |
| Progress | Display observed position/duration; preview and submit one absolute seek on release when seekability and duration are known |
| Shuffle | Emit the explicit opposite of the known observed value for an active queue |
| Repeat | Emit off → all → one → off for an active queue |
| Queue | Open the four-item page containing the observed current item; Earlier/More page through bounded reads |
| Queue item | Emit its zero-based index; requires active queue playback and a matching observed revision |
| Refresh in room/queue views | Retry reads; no playback intent |

Selecting a different room clears all metadata and the page at admission, before network discovery. The worker reads the selected room independently. Selection persists its display ID in the existing `surface/preferred-id` key; accepted mutations still freeze UUID and policy. USB `room-select bedroom` exercises this same selection path. Selecting a room never resumes it or replaces its source.

Queue rows show title/artist and distinguish the current item. A non-queue source may expose its stored queue, labeled as stored and unavailable for selection. The shared application retains only one page and invalidates it at reconciliation. The queue screen requests its visible page again after invalidation; errors wait for explicit Refresh instead of retrying continuously. A shrunken queue moves an out-of-range page to its new final page. No entire-queue read or extra UI cache is introduced. Polling remains nominally ten seconds; queue reads include a state refresh and share the serialized worker. Input during another user action rejects visibly ("Busy - try again"); it is not silently queued or replayed. An automatic poll in progress shows "Updating..." but never rejects input.

## State and touch behavior

Observed state remains authoritative. Previews disappear on release, rejection, room/content replacement, multi-touch, invalid coordinates, or peripheral recovery. No preview is written into AppState. Mutating gestures reject stale/offline state and unresolved command uncertainty. A rendered seek/queue request also carries its displayed content/revision for admission checking; the existing adapter then performs its fresh execution checks. External edits still have the documented non-atomic Sonos race; there is no cross-controller transaction.

`READ ONLY` is permanently visible when the runtime setting is true. Controls remain visible, with unavailable capabilities dimmed. Read-only attempts describe the intended action, pass through normal validation/policy/planning, and are blocked at the shared HTTP boundary. A request already satisfied by observation may require no write; the UI reports no change sent rather than claiming a new mutation. Feedback lasts 3.5 seconds and does not replace the playback layout. Observation errors, offline/stale state, and recovery requirements remain visible.

Normal gestures use stored calibrated coordinates for every sample. LVGL finds the widget under a press; the portable model keeps the gesture rules. Buttons activate on release only when the press started on them and stayed within 16 pixels; sliding off a button (LVGL press-lost) or onto another cancels the tap. Sliders keep the press wherever the finger goes (press lock): LVGL starts moving the knob after about 10 pixels of motion, sets it at the release point for a plain tap, clamps it to the visible endpoints, and reports each knob position to the model as the preview. Calibration changes, peripheral failures, and screen changes require release before rearming. The raw six-target diagnostic, `display-edge`, and `peripherals-retry` remain.

## Layout and implementation limits

`WaveshareUi.h` owns the small portable Now Playing interaction model and the accepted control rectangles. `WaveshareShell.h` owns the portable top-level navigation state, the BOOT button, and touch ownership. `WaveshareLvgl.cpp` builds the LVGL screens from those rectangles and owns the display flush, the pointer input device, and every widget. `Waveshare.cpp` retains peripheral initialization, touch sampling/calibration, and the known-good PSRAM canvas/full-frame CO5300 flush. `Runtime.cpp` admits typed UI intents and selection/page actions to the existing worker. Shared core and Sonos adapter files contain no screen, gesture, or layout concepts.

Controls sit within x=32–336/y=28–416, with slider endpoints x=52/316. Their centers fit the saved unit's reachable calibration area; the owner has accepted this layout and artwork appearance. That does not establish full-screen accuracy. The built-in Montserrat fonts (14, 20, and 28 px) provide ASCII plus a few symbols; other UTF-8 codepoints render as a placeholder box, never as broken byte fragments. Text is bounded and ellipsized rather than wrapping into other controls. Title uses two lines, artist one line, and album one compact line.

## Album artwork

The 64×64 record placeholder now displays the current cover when available. A separate low-priority worker downloads the normalized speaker HTTP artwork URL and decodes baseline JPEG using the decoder already included in pinned Arduino-ESP32 **3.3.11**. No new dependency, media library, or persistent cache is introduced. The touch layout, including volume, is unchanged.

Only one job can be in flight. Changing room, track identity, or artwork URL immediately removes the visible cover and advances a generation; late results are discarded. A changed generation also aborts an active body download at its next chunk. The UI never waits for HTTP or decoding. State polling and queue reads keep their existing worker; artwork does not hold its busy flag or locks. Only the current 8,192-byte RGB565 thumbnail remains resident after completion.

The image body is capped at **256 KiB**, input dimensions at **2048×2048**, and scaled decoder output at **128 KiB**, allocated in PSRAM. Baseline JPEG is decoded at a supported 1/2, 1/4, or 1/8 scale where useful, then fit into the square with black padding for non-square images. Connect timeout is 1.5 seconds, inactivity timeout 2 seconds, and body processing has a 6-second deadline checked at chunks (an in-flight read can add its inactivity timeout). The worker stack is 8 KiB. The accepted image bounds also bound decoding work.

HTTP errors, excessive size/dimensions, missing artwork, PNG, progressive JPEG, and HTTPS-only URLs retain the placeholder. No redirects, insecure TLS bypass, or credentials are used. Transient failures retry at most every 30 seconds while online with non-stale state; unsupported HTTP image formats share that bounded retry interval. Empty, overlong, or non-HTTP URLs are not requested. Other image formats/TLS are follow-ups if observed household artwork requires them.

Serial `[artwork]` lines measure fetch/decode/total latency, working heap/PSRAM, before/after memory, and generation publication/discard. Rendering still uses one full-frame canvas flush. Progress uses real observations without interpolation; full playback event subscriptions remain deferred.

Serial `[lvgl] frame` lines report, for every touch-driven frame, touch-to-flush and sample-to-handler latency, render and flush time, flushed pixels, the maximum main-loop poll gap since the previous frame, free heap, and free PSRAM; `[lvgl] stats` summarizes every five seconds, and `[ui] frame` marks each sync of the widgets from the model. Queue diagnostics measure the bounded page fetch separately from discovery/state refresh. USB `ui-screen now|rooms|queue|grouping|playground` shows a screen (or a Now Playing sub-view) for serial layout/performance inspection without injecting touches or issuing a playback intent. `ui-state` prints one JSON line with the top-level `screen` and Now Playing `view`, page offsets, contact and previews, toast, busy/online/read-only, the observed playback values, the last touch sample, the playground slider value and click counts, the last frame's costs, and free heap/PSRAM. Touch logs retain raw/mapped coordinates, the widget under the sample, and release actions. These are live serial diagnostics, not stored history. See [hardware evidence](hardware.md) for measured performance and limitations.

`ui-touch X Y [fingers]`, `ui-touch release`, and `ui-button boot` inject input for host-driven verification. An injected sample is already in calibrated screen coordinates, so it replaces one hardware sample per touch poll after the calibration step and changes nothing else: it enters the same interaction model, obeys the release-after-boot rule, and passes through admission, `read_only`, and policy exactly as a finger does. Samples queue in order with a bounded depth of 32, and any physical contact cancels the rest. A gap between host commands is not a lifted finger: an open injected gesture keeps the screen until its release arrives, or until a bounded 1.5-second timeout returns the screen to hardware sampling, whose next no-contact sample releases the gesture exactly as a lifted finger would. Injected input records no local activity and never postpones sleep. `ui-screen`, `ui-state`, and the injection commands are all disabled in the raw touch-diagnostic build.

BOOT is sampled by the adapter as a debounced button: the raw low level is local activity exactly as before, and the action is the release edge of a press that outlasts 30 ms and lasts no longer than one second; a longer hold performs nothing. The press that woke or booted the device is consumed, so no press counts until a release has been seen. The action moves to the next top-level screen. `ui-button boot` injects that completed short press and `ui-nav next` performs its action directly; neither is local activity.

## Screens and LVGL architecture

LVGL 9 (pinned in `scripts/common.ts`, configured by the repo-owned `libraries/SurfaceDevice/src/lv_conf.h`) owns widgets, hit-testing, dragging, scrolling, screens, and invalidation on ws-1.8. The application owns authoritative state: observed values flow AppState → the portable model → widgets, and widget events flow into the model, whose release-to-submit rules produce the same BoardEvents as before; a widget value is never state. Hardware adapters own the display and touch details: the display path is fixed to DIRECT render mode into the existing PSRAM canvas with one full-frame flush per refresh, because partial windows tear on this panel (see [hardware evidence](hardware.md#waveshare-rendering-and-calibration)), and the calibrated (or injected) sample is the single input-device path. The Arduino main task owns every LVGL call: the Sonos worker and artwork tasks publish state under their existing locks and the main task syncs widgets from its copy on the render cadence. LVGL timers, animations, redraws, and injected input never count as local activity, and LVGL stops before the panel powers down for sleep. stick-s3 does not link LVGL. LVGL's own allocations (widgets, styles, label texts, draw buffers) go through the custom allocator in `WaveshareLvgl.cpp`, which prefers PSRAM and falls back to internal SRAM, so internal heap stays for networking: idle free heap is about 140 KB against about 154 KB before LVGL, and the image is about 289 KB larger.

| Screen | `ui-screen` | Content |
| --- | --- | --- |
| Now Playing | `now` (`rooms` and `queue` show its sub-views) | The accepted playback UI above; Rooms and Queue are containers inside this screen, reached from the room header and the Queue button and dismissed with Back |
| Grouping | `grouping` | Placeholder shell only; grouping arrives in a later milestone |
| Playground | `playground` | Development screen for interaction experiments: 44/32/24 px tap-target rows with click counters, a local slider, a finger-tracking pad, and a scrolling list, all inside the reachable area. Nothing on it reaches the model or Sonos, and its layout is disposable |

Navigation is UI state only, never persisted: every boot and wake starts on Now Playing, BOOT (or `ui-nav next`) cycles Now Playing → Grouping → Playground → Now Playing, and a room change never changes the top-level screen. The cycle discards an open sub-view, so returning to Now Playing shows Now Playing itself. There is no swipe, edge, hidden-zone, multi-click, or long-press navigation. Each top-level screen is one LVGL screen object built at boot and switched with `lv_screen_load`; before the switch the adapter drops the input device's active press and holds a contact still down until it lifts, so a press started on one screen cannot complete on another, and the model cancels its gesture, so a volume or seek preview active at navigation submits nothing. Touch reaches only the active screen; accepted Sonos work, observed state, and the selected room are untouched by a screen change. Every widget stays inside the calibrated reachable area and corner mask (x=32–336, y=28–416, slider endpoints x=52/316) with targets of at least 32 px, 44 px for anything important.

## Accepted prototype scope

The owner accepted this 1.8-inch layout and artwork, including a cover change following an externally selected album. Some mistaps on the small screen remain acceptable for the owner's prototype. The volume slider is experimental UI; a future larger kids-room UI is expected to use +/- volume buttons. Shared volume remains the normal logical 0–100 range; no application volume limiter is implemented. Deployment guidance lives in [README](../README.md#configuration).

Mode buttons submit no-source explicit intents. They retain generic queue-mode capability, including repeat-one, without inferring an incoming declarative source from current playback. New source-card validation and defaults live in [intent](intent.md#source-specific-mode-validity) and [policy](policy.md).
